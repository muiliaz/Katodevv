## В двух словах

Здесь мы отступили от порядка, который сами же наметили в плане: тесты (P1) сделали раньше
лимитера (P0). Причина простая — следующий шаг лезет внутрь обеих публичных функций, а их поведение
не было закреплено вообще ничем. Сначала зафиксировали, как всё работает сейчас, и только потом
пошли менять.

Написали 24 теста. Чтобы убедиться, что они не декоративные, специально сломали код в двух местах и
посмотрели, покраснеет ли прогон — покраснел.

## Проблема

Аудит качества тестов (итог 39/100) назвал это первым по важности шагом:

> **Покрыть Netlify handlers напрямую.** Почему важно: публичные `contact.js` и `lead.js` обрабатывают
> заявки, но сейчас проверяется лишь общая валидация. Первый шаг: добавить Jest-тесты `handler(event)`
> для success, non-POST, invalid JSON, validation error, honeypot и Telegram failure с mock `sendMessage`.
> Готово, когда оба handlers имеют позитивные и отказные сценарии в CI.

Та же дыра отмечена ещё в двух отчётах — это и определило приоритет:

| Аудит | Формулировка |
|---|---|
| tests | «Integration-тесты покрывают границы компонентов — 2/5: есть mocked `fetch`, но handlers, env и Telegram-клиент не интегрированы» |
| vulns | шаг 3: «Покрыть оба маршрута тестами: первый допустимый запрос проходит, превышение лимита не вызывает `sendMessage`, отказ ограничителя обрабатывается закрытым образом» |
| cognitive-debt | «Не доказаны единым сценарием полный chat-to-lead поток, совместимость его payload с `validateLead`, доставка в Telegram» |

Фактическое состояние до шага: два тестовых файла, 15 тестов. Покрывалась форма Contact (на уровне
React-компонента) и **чистые функции валидации**, импортированные напрямую. Сами `handler(event)` —
то есть то, что реально вызывает Netlify по публичному URL, — не выполнялись в тестах ни разу.

Из-за этого без покрытия оставались склейка валидации с отправкой, ветка honeypot, обработка не-POST,
поведение при падении Telegram, формирование текста сообщения и экранирование на пути в Telegram.

## Ход рассуждения

### Почему этот шаг сделан раньше P0-шага 03 (rate limiting)

Это единственное отступление от порядка приоритетов, заданного в задаче, и оно намеренное.

Шаг 03 добавляет лимитер **внутрь обоих handler-ов** — то есть меняет поведение публичного кода,
которое на данный момент не закреплено ничем. Если писать тесты после лимитера, они будут написаны
по факту уже изменённого кода: любая регрессия, внесённая на шаге 03, окажется зафиксирована как
«ожидаемое поведение», и тесты её не поймают — они её узаконят.

В обратном порядке тесты работают как сетка: они описывают контракт «до», и если шаг 03 его
нарушит, прогон покраснеет. Ровно эту роль они и сыграют.

Стоимость отступления — то, что находка Medium из аудита vulns закрывается на один шаг позже.
P0-находка Low (шаг 01) при этом уже закрыта, а шаг 03 идёт следующим, так что задержка измеряется
одним коммитом.

### Где физически размещать тесты

Ограничение диктует Create React App: его Jest-конфигурация подхватывает тесты только внутри `src`.
Функции лежат в `frontend/netlify/functions`, то есть **вне** `src`.

| Вариант | Оценка |
|---|---|
| Положить тесты рядом с функциями (`netlify/functions/contact.test.js`) | Отклонён. CRA их не увидит, значит они не попадут в `npm run test:ci` и в CI. Тест, который не запускается, хуже отсутствующего — он создаёт ложное чувство покрытия |
| Настроить отдельный Jest-конфиг для функций и второй скрипт `test:functions` | Отклонён. `react-scripts test` не отдаёт управление конфигом Jest без `eject`; пришлось бы ставить отдельный Jest со своим babel-обвесом. Это добавляет второй тестовый тулчейн ради двух файлов и вторую команду, которую CI придётся не забыть вызвать |
| Тесты в `src/__tests__/`, импорт функций по относительному пути | ✅ **Выбран.** Это уже устоявшийся в проекте приём: `src/__tests__/netlifyValidation.test.js` делает ровно так и объясняет причину в шапке файла. Новые тесты следуют существующему решению, а не изобретают второе |

Комментарий из существующего файла, на который мы опирались:

```js
// Tests for the Netlify functions' shared input validation.
// The test lives under src/ because create-react-app's Jest setup only picks up
// test files there; the module itself is imported from the functions folder.
```

### Насколько глубоко мокать

Ключевое решение: `sendMessage` мокается, `escapeHtml` — **нет**.

| Вариант | Оценка |
|---|---|
| `jest.mock(path)` — автомок всего модуля | Отклонён. Тогда `escapeHtml` тоже станет заглушкой и вернёт `undefined`, а вместе с ним развалится сборка текста сообщения. Хуже того: любое утверждение об экранировании стало бы проверкой мока, а не кода — то есть декоративным тестом, ровно того сорта, которых аудит в текущем наборе не нашли и которые не стоит заводить |
| Мокать глобальный `fetch` вместо модуля Telegram | Отклонён. Это тестировало бы заодно и `sendMessage`, но привязало бы тесты handler-ов к формату запросов Telegram API. При смене транспорта посыпались бы тесты обоих handler-ов, хотя их логика не менялась |
| Частичный мок: реальный модуль + подменённый `sendMessage` | ✅ **Выбран** |

```js
jest.mock("../../netlify/functions/lib/telegram", () => {
  const actual = jest.requireActual("../../netlify/functions/lib/telegram");
  return { ...actual, sendMessage: jest.fn() };
});
```

Это даёт две вещи сразу. Во-первых, границей мока становится ровно сетевой вызов — всё, что до него,
исполняется по-настоящему. Во-вторых, утверждения вида «`<b>Ada</b>` превратилось в `&lt;b&gt;Ada&lt;/b&gt;`
в тексте, ушедшем в `sendMessage`» доказывают реальное экранирование реальной функцией, а не поведение
заглушки.

Мок применяется корректно, несмотря на разные пути импорта (handler делает `require('./lib/telegram')`,
тест — `require('../../netlify/functions/lib/telegram')`), потому что реестр модулей Jest ключуется по
разрешённому абсолютному пути, а он совпадает.

### Два файла или один

Выбрали два — `netlifyContact.test.js` и `netlifyLead.test.js`. У handler-ов разные payload'ы, разные
правила валидации и разная форма сообщения; общий файл потребовал бы либо параметризации, которая
скрыла бы эти различия, либо двух наборов фикстур в одной области видимости. Отдельные файлы также
дают понятную зернистость при падении в CI.

### Что тестировать про `console.error`

Добавили по одному тесту в каждом файле на то, что деталь ошибки **всё-таки логируется**. Логика:
шаг 01 убрали текст ошибки из ответа, и есть реальный риск, что при будущем рефакторинге кто-то
уберёт заодно и логирование — тогда сбой станет полностью невидимым и для клиента, и для оператора.
Тест закрепляет, что скрытие от вызывающего не означает скрытия от владельца.

Заодно `console.error` замокан во всех тестах, иначе прогон засоряется stack trace'ами от намеренно
вызванных сбоев.

## Diff / ключевые фрагменты

Частичный мок и утверждение об экранировании — суть подхода:

```js
jest.mock("../../netlify/functions/lib/telegram", () => {
  const actual = jest.requireActual("../../netlify/functions/lib/telegram");
  return { ...actual, sendMessage: jest.fn() };
});

const sentText = () => sendMessage.mock.calls[0][0];

test("escapes user input so it cannot inject Telegram HTML markup", async () => {
  await post({ ...validContact, name: "<b>Ada</b>", message: "5 < 6 & 7 > 6, please build it." });

  expect(sentText()).toContain("&lt;b&gt;Ada&lt;/b&gt;");
  expect(sentText()).toContain("5 &lt; 6 &amp; 7 &gt; 6");
  // The bold tags that remain are the handler's own formatting, never the user's.
  expect(sentText()).not.toContain("<b>Ada");
});
```

Проверка, что отказ Telegram не ретранслируется наружу (регрессионный тест на фикс шага 01):

```js
test("does not echo a Telegram rejection back to the client", async () => {
  sendMessage.mockRejectedValue(new Error("Bad Request: chat not found"));

  const res = await post(validContact);

  expect(res.statusCode).toBe(500);
  expect(JSON.parse(res.body)).toEqual({ error: GENERIC_ERROR });
  expect(res.body).not.toContain("chat not found");
});
```

Honeypot — с объяснением, почему код ответа именно 200:

```js
test("answers a honeypot hit with a plain success and sends nothing", async () => {
  // A bot filled the hidden "company" field. It must get no signal that it
  // was spotted, so the status code is indistinguishable from a real success.
  const res = await post({ ...validContact, company: "spam-co" });

  expect(res.statusCode).toBe(200);
  expect(JSON.parse(res.body)).toEqual({ success: true });
  expect(sendMessage).not.toHaveBeenCalled();
});
```

## Риски и что осталось

### Риски внесённого изменения

Нулевые для продакшена: добавлены только тестовые файлы, рабочий код не тронут. Время прогона
выросло незначительно (0,4 с на полный набор).

### Что этот шаг НЕ доказывает

Важно не переоценить результат:

1. **Реальная доставка в Telegram не проверяется.** `sendMessage` замокан. Что запрос уходит на
   верный URL с верным `parse_mode` — по-прежнему держится только на ручной проверке. Покрытие
   `telegram.js` 21%.
2. **Браузерный путь не проверяется.** Аудит тестов ставит 0/5 за «E2E-тесты проверяют бизнес-ценность»;
   этот шаг там ничего не меняет. Что `ChatWidget` формирует payload, совместимый с `validateLead`,
   всё ещё не доказано сквозным сценарием — это отдельная рекомендация cognitive-debt («Chat-to-lead:
   добавить интеграционную спецификацию»), и она остаётся открытой.
3. **Покрытие React-части не выросло** — оно как было 2,23%, так и осталось. Эти тесты про серверную
   часть.

### Зафиксированный дефект, который здесь только задокументирован

Битый JSON отдаёт **500**, хотя это ошибка вызывающего и семантически должна быть **400**. Тесты в
обоих файлах фиксируют текущее поведение с явным комментарием:

```js
// Documents current behaviour: the JSON.parse sits inside the same try as
// the rest, so a bad body is reported as a server error rather than a 400.
expect(res.statusCode).toBe(500);
```

Это сознательно оставлено как есть на этом шаге: сначала контракт закрепляется, потом меняется.
Исправление запланировано на шаг 03, где handler-ы всё равно перерабатываются под лимитер — тогда
же тесты будут переписаны на 400. **Если шаг 03 это не сделает, дефект остаётся открытым.**
