# 04 — CI как блокирующий гейт

**P0** · аудит cicd, единственный критерий с нулём · 2026-08-05

## Проблема

Workflow существовал и выглядел корректно, но `main` не требовала его прохождения. С учётом того,
что `main` автодеплоится на katodevv.com, красный merge — это красный прод.

## Что сделали мы, что — владелец

Включение защиты ветки — действие в настройках GitHub, прав у нас нет. Поэтому: прогнали все шаги
локально (гейт не покраснеет при включении) и написали инструкцию.

**Поправка от 2026-08-06.** Изначально написали, что подтвердить запуск невозможно — «gh не
установлен, доступа к GitHub API нет». Первое верно, второе **не проверяли**, и оно оказалось
неверным. API отвечает. Фактически: два запуска, на текущем `main` — success. То есть находка
«успешная работа CI не подтверждена» была закрыта ещё до нас.

**Имя проверки — `build`.** Подтверждено составом реального запуска, а не догадкой по YAML. Это
место, где опечатка навсегда блокирует ветку, поэтому выбирать надо из выпадающего списка.

## Проверка

Гейт включён владельцем и проверен на деле — попытка запушить сломанный коммит прямо в `main`:

```
remote: error: GH013: Repository rule violations found for refs/heads/main
remote: - Required status check "build" is expected.
! [remote rejected] main -> main
```

Это сильнее блокировки кнопки Merge: останавливает даже прямой push.

## Осталось

Откат неудачного деплоя: Netlify → Deploys → последний рабочий → ⋯ → Publish deploy. Пересборка не
нужна. Стоит проверить заранее, а не в момент аварии.
