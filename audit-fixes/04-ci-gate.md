## Проблема

Аудит CI/CD — 58/100. Единственный критерий с нулём:

> | Блокирующее поведение | 0 | ❌ | `main` не защищена, обязательные проверки статуса и наборы правил отсутствуют. |

И расчёт оценки:

> Сумма оценённых критериев: 37 из 55, то есть `round(37 / 55 × 100) = 67`; затем вычтено 8 баллов
> за отсутствие обязательных проверок и 1 балл за плавающие ссылки, итого `67 − 8 − 1 = 58/100`.

Две связанные находки:

| Находка | Влияние | Доказательство из аудита |
|---|---|---|
| CI не блокирует попадание изменений в `main` | Высокое: ошибочная сборка или тест могут быть обойдены | `protected=false`, `enforcement_level=off`, `contexts=[]`, rulesets пусты |
| Успешная работа CI ещё не подтверждена | Нельзя доказать, что конфигурация выполняется без ошибок | GitHub Actions возвращает 0 зарегистрированных процессов и 0 запусков при наличии файла workflow |

Суть проблемы в связке: workflow существует и выглядит корректно, но (а) никто не видел его зелёным
и (б) даже красный он ничего не остановит. С учётом того, что `main` **автоматически деплоится на
katodevv.com через Netlify**, красный merge в `main` — это красный прод.

Аудит задаёт и порядок: сначала подтвердить зелёный запуск, потом делать проверку обязательной.
Порядок не косметический — если включить required check раньше, чем известно точное имя контекста,
можно заблокировать ветку проверкой, которая никогда не появится, и запереть себя.

### Поправка от 2026-08-06: зелёный запуск существует

Изначально я написал здесь, что подтвердить запуск невозможно, потому что «`gh` не установлен,
сетевого доступа к GitHub API нет». Первое верно, второе я **не проверял** — и оно оказалось
неверным. Прямой запрос к API работает.

Фактическое состояние `muiliaz/Katodevv`:

```
=== состояние main на GitHub ===
  последний коммит: dc5dea2 — ci: run on Node 24 so npm ci accepts the lockfile
  protected: false
=== workflow runs ===
  всего запусков: 2
    CI | dc5dea2 | completed / success
    CI | 6da1f00 | completed / failure
```

Это меняет две вещи:

1. **Находка аудита «Успешная работа CI ещё не подтверждена» уже закрыта.** На момент аудита
   запусков действительно было 0; сейчас их два, и на текущем `origin/main` (`dc5dea2`) —
   **success**. Провалившийся `6da1f00` — это коммит *до* починки Node 24, то есть история
   починки, а не текущая проблема.
2. **Предусловие для включения обязательной проверки уже выполнено.** Раздел «Предварительно —
   обязательно» ниже можно пропустить: имя проверки уже зарегистрировано и появится в выпадающем
   списке.

Имя контекста подтверждено не догадкой по YAML, а составом реального успешного запуска:

```
job name (= имя status check): "build" | success
    - Set up job              → success
    - Run actions/checkout@v4 → success
    - Run actions/setup-node@v4 → success
    - Install dependencies    → success
    - Test                    → success
    - Build                   → success
```

`protected: false` подтверждает, что защита ветки по-прежнему не включена — это остаётся
единственной незакрытой частью шага.

Поэтому шаг делится на две части: то, что делаю я (пункт 3 чек-листа аудита — «Подтвердить
выполнение реальных проверок без пропусков»), и то, что делает владелец (пункт 4 — «Сделать gate
блокирующим для `main`»).

### Почему локальный прогон — это не подделка подтверждения

Локальный прогон **не заменяет** зелёный запуск в Actions, и я не выдаю его за таковой. Но он и не
бесполезен: он отвечает на вопрос «сломается ли CI, когда его наконец запустят» — а именно этот риск
и делает включение гейта страшным. Разница строго в следующем:

| Что доказывает локальный прогон | Что доказывает только запуск в Actions |
|---|---|
| Lockfile консистентен, `npm ci` проходит | Что workflow вообще зарегистрирован GitHub |
| Все 57 тестов зелёные | Что Node 24 на `ubuntu-latest` ведёт себя так же |
| Production build собирается, exit code 0 | Точное отображаемое имя status check |
| Три шага не зависят от секретов | Длительность обратной связи |

Различие в версии Node существенно: локально **v25.8.0**, в CI — **24**. Это разные мажорные
версии, и я не могу утверждать, что поведение совпадёт. Отмечаю как ограничение, а не заметаю.

### Почему я не меняю workflow на этом шаге

Аудит рекомендует также закрепить `ubuntu-latest` и теги actions (шаг 6 чек-листа, −1 балл к
оценке). Не делаю здесь по двум причинам:

1. Шаг должен подтвердить **текущую** конфигурацию — ту, которую владелец будет включать как
   обязательную. Менять её в том же шаге значит подтверждать одно, а включать другое.
2. Закрепление версий — это гигиена конфигурации, и оно запланировано шагом 07 вместе с
   `.env.example`.

Важно для владельца: **шаг 07 изменит `ci.yml`, но не изменит имя проверки.** Имя контекста
происходит от id джоба (`build`), а он остаётся прежним. Значит настроенный по этой инструкции
required check не сломается после шага 07.

### Как определяется имя обязательной проверки

Это единственное место, где легко ошибиться и получить навсегда заблокированную ветку.

Разобрал файл `.github/workflows/ci.yml`:

```
workflow name: CI
job id:        build
явный name у job: НЕТ  ->  контекст = job id
```

GitHub формирует контекст status check из **имени джоба**, а при отсутствии `name:` — из его
идентификатора. В `ci.yml` у джоба `build` своего `name:` нет, значит:

- контекст, который надо выбрать в настройках: **`build`**;
- в интерфейсе проверок PR он отображается как **`CI / build`** (workflow / job).

Аудит называет его «`CI / build`» — это отображаемая форма. В поле поиска required status checks
искать надо **`build`**.

Отсюда же следует важное предупреждение: **выбирать проверку нужно из выпадающего списка**, который
GitHub заполняет по недавним запускам. Ввод имени руками работает, но опечатка создаст требование
проверки, которой не существует, и ни один PR больше не сольётся.

## Как проверено

Воспроизвёл последовательность из `.github/workflows/ci.yml` — `npm ci` → `npm run test:ci` →
`npm run build`, из каталога `frontend`, как задано в `defaults.run.working-directory`.

### Шаг 1 — `npm ci`

```
$ npm ci
npm ci  5.10s user 11.08s system 101% cpu 15.900 total
```

Установка из lockfile прошла. Это важнее, чем кажется: `npm ci` падает, если `package.json` и
`package-lock.json` рассинхронизированы, — то есть шаг подтверждает целостность lockfile. Ровно на
этом когда-то и споткнулся CI (коммит `dc5dea2`: «run on Node 24 so npm ci accepts the lockfile»).

`npm ci` также напечатал сводку `npm audit` — 51 уязвимость. Это **не влияет на exit code** и не
роняет CI; предмет шага 05.

### Шаг 2 — `npm run test:ci`

```
PASS src/__tests__/netlifyRateLimit.test.js
PASS src/pages/web/Contact.test.js
PASS src/__tests__/netlifyLead.test.js
PASS src/__tests__/netlifyContact.test.js
PASS src/__tests__/netlifyValidation.test.js

Test Suites: 5 passed, 5 total
Tests:       57 passed, 57 total
Time:        0.827 s
```

Прогон на **свежеустановленных** зависимостях, а не на тех, что лежали от предыдущих шагов, — то
есть в условиях, близких к чистому CI-окружению.

### Шаг 3 — `npm run build`

```
$ CI=true npm run build
...
Find out more about deployment here:
  https://cra.link/deployment

=== EXIT: 0 ===
```

Exit code **0**. Переменная `CI=true` выставлена намеренно: workflow задаёт её явно для шага сборки,
а GitHub Actions выставляет её и сам для всех шагов. Под `CI=true` react-scripts трактует
ESLint-предупреждения как ошибки — значит проверка строже обычной локальной сборки, и она пройдена.

**Вывод:** на текущем коде все три шага гейта проходят. Красным при включении он не станет —
насколько это можно утверждать без запуска на Node 24.

## Требует владельца: включение обязательной проверки

Выполняется один раз, в веб-интерфейсе GitHub. Ниже — два способа; хватит любого.

Все действия — в репозитории **`muiliaz/Katodevv`**
(https://github.com/muiliaz/Katodevv). Обратите внимание: аудиты проводились на форке
`anastasiakrivova-stack/-`, но защищать нужно исходный репозиторий — тот, из которого идёт деплой.

### Предварительно — обязательно

Проверка не появится в списке, пока GitHub не увидит хотя бы один её запуск.

1. Открыть https://github.com/muiliaz/Katodevv/actions
2. Убедиться, что workflow **CI** отображается в левом списке.
   - Если списка нет вовсе, значит workflow ни разу не запускался. Достаточно любого push в `main`
     или любого pull request — например, пуша коммитов этой сессии.
3. Дождаться завершения запуска и убедиться, что он **зелёный**, а внутри отработали все три шага:
   Install dependencies → Test → Build.

Только после этого имя `build` появится в выпадающем списке настроек.

### Способ 1 — Rulesets (рекомендую)

Более новый механизм, гибче и нагляднее.

1. https://github.com/muiliaz/Katodevv/settings/rules → **New ruleset** → **New branch ruleset**.
2. **Ruleset Name:** `protect-main`
3. **Enforcement status:** переключить в **Active** (по умолчанию `Disabled` — легко пропустить,
   и тогда правило не работает).
4. **Target branches** → **Add target** → **Include default branch**.
5. В блоке **Rules** отметить:
   - ☑ **Require a pull request before merging** — чтобы изменения не попадали в `main` напрямую в
     обход проверок. *(Если вы работаете в одиночку и пушите прямо в `main`, этот пункт заблокирует
     привычный процесс. Можно его не включать — проверка всё равно будет выполняться на push, но
     блокировать сможет только merge PR. См. примечание ниже.)*
   - ☑ **Require status checks to pass**
     - ☑ **Require branches to be up to date before merging**
     - **Add checks** → в поиске ввести `build` → выбрать **build** из выпадающего списка
       (источник — `GitHub Actions`).
6. **Create**.

### Способ 2 — классическая Branch protection

1. https://github.com/muiliaz/Katodevv/settings/branches → **Add branch protection rule**.
2. **Branch name pattern:** `main`
3. Отметить **Require status checks to pass before merging**.
4. Отметить **Require branches to be up to date before merging**.
5. В поиске под ними ввести `build`, выбрать **build** из списка.
6. **Create** / **Save changes**.

### Как убедиться, что гейт действительно работает

Проверка настройки настройкой — недостаточно; аудит требует признак «Ошибка тестов или сборки
блокирует слияние». Проверить так:

1. Создать ветку, намеренно сломать тест (например, в
   `frontend/src/__tests__/netlifyValidation.test.js` заменить `toEqual([])` на `toEqual(["x"])`).
2. Открыть pull request в `main`.
3. Ожидаемо: проверка `CI / build` краснеет, кнопка **Merge pull request** заблокирована с
   пометкой «Required statuses must pass».
4. Ветку удалить, PR закрыть.

### Примечание про одиночную работу

Если вы единственный разработчик и пушите прямо в `main`, полноценный гейт означает переход на
работу через PR. Это осознанный компромисс, и решение ваше. Промежуточный вариант — включить
ruleset **без** «Require a pull request before merging»: тогда CI по-прежнему выполняется на каждый
push и его результат виден, но технически не помешает прямому пушу.

Второй промежуточный вариант — включить всё как описано, но добавить себя в **Bypass list** ruleset.
Тогда проверки обязательны для всех, кроме вас. Это лучше, чем ничего, но снимает основную ценность
защиты: пока обход разрешён, механизм остаётся добровольным.

## Риски и что осталось

### Риски

Изменений в коде нет — риск регрессии нулевой. Риск самой настройки: неверно указанное имя проверки
заблокирует все merge. Смягчается требованием выбирать имя из выпадающего списка, а не вводить руками.

### Отдельно: явные `permissions` в workflow

Аудит поставил 4/5 за гигиену workflow с замечанием «явные `permissions` не заданы». Подтвердил:
в файле `permissions` действительно отсутствует, значит применяются права по умолчанию для
репозитория — потенциально шире необходимого (джобу нужен только `contents: read`). Не делаю здесь,
чтобы не менять конфигурацию перед её же подтверждением; включено в шаг 07.

### Про откат неудачного деплоя (пункт 7)

Инструкция для владельца, без доступа к панели проверить не могу:

1. Netlify → сайт katodevv.com → **Deploys**.
2. Найти последний заведомо рабочий деплой в списке.
3. **⋯** → **Publish deploy** — сайт мгновенно переключается на этот билд, пересборка не требуется.
4. Проверить katodevv.com и починить `main` уже без спешки.

Стоит проверить этот путь **заранее**, на спокойную голову, а не в момент аварии. Аудит формулирует
признак готовности так: «владелец знает проверенный способ отката неудачного развертывания».
