## В двух словах

Самый низкий балл из всех аудитов и самый рискованный шаг: любая правка здесь трогает lockfile,
то есть может тихо сломать сборку. Поэтому шли от безопасного к рискованному и после каждого

обновления роутера тесты и сборка были зелёными, а тестовый раннер на самом деле лежал — просто

## Ход рассуждения

### Порядок: от безопасного к рискованному

Все действия здесь трогают `package-lock.json`, то есть ровно то, что может тихо сломать сборку.
Поэтому шли от наименее рискованного к наиболее, проверяя тесты и сборку после каждого шага, а не
одним пакетом изменений в конце. Это дало возможность точно локализовать поломку, когда она
случилась (а она случилась — см. раздел про роутер).

### Шаг A — `npm audit fix` без `--force`

Начали с самого безопасного: штатный `npm audit fix` меняет только lockfile и только в пределах
допустимых semver-диапазонов, объявленных в `package.json`.

Результат: **51 → 31**, обе critical закрыты, `package.json` не изменился (`diff` пустой).

Осознанно **не** использовал `npm audit fix --force`. На этом проекте он предложил бы
`react-scripts@0.0.0` — то есть снёс бы сборщик вместе со сборкой и тестами.

### Шаг B — `react-router-dom` 6 → 7 (DH-001)

Поверхность использования узкая, проверили её перед обновлением:

```
src/app/App.js:2            BrowserRouter, Routes, Route
src/pages/bots/Bots.js:2    Link
src/pages/web/Navbar.js:2   Link
src/pages/apps/Apps.js:1    Link
src/pages/hub/Hub.js:2      Link
src/pages/hub/LaserShowcase.jsx:2   useNavigate
```

Пять API, все с неизменившимся контрактом в v7. Отсюда — оценка риска как низкой.

**Здесь и вскрылась главная проблема шага.** После установки `react-router-dom@7.18.2` тесты и
сборка прошли зелёными. Но зелёный прогон ничего не значил: **ни один существующий тест не касался
роутинга**. `Contact.test.js` рендерит компонент напрямую, без `BrowserRouter`.

Поэтому написали `src/__tests__/routing.test.js` — и он немедленно упал двумя разными способами:

**Поломка 1.** `Cannot find module 'react-router/dom'`

`react-router` v7 публикуется с subpath-экспортами (`"./dom"` в поле `exports`), а Jest 27, который
идёт в составе `react-scripts` 5, поле `exports` не резолвит.

**Поломка 2 (после починки первой).** `ReferenceError: TextEncoder is not defined`

`react-router` v7 обращается к `TextEncoder` на этапе импорта. В Node этот глобальный объект есть
много лет, но jsdom из состава Jest 27 его не предоставляет.

Обе поломки — **только в тестовой среде**; production build собирался нормально в обоих случаях,
потому что webpack `exports` резолвит, а в браузере `TextEncoder` есть. То есть без нового теста
обновление уехало бы «зелёным» с неработающим тестовым раннером.

Это, кстати, и есть аргумент в пользу находки DH-002: **сборщик из 2022 года ограничивает
обновление обычной зависимости 2026 года**.

Как чинили:

| Поломка | Рассмотренные варианты | Выбор |
|---|---|---|
| `react-router/dom` не резолвится | (1) откатиться на v6 — отменяет DH-001; (2) `eject` — необратимо и вываливает 200+ строк конфига; (3) `moduleNameMapper` в поле `jest` | (3). CRA разрешает переопределять `moduleNameMapper` — проверили по `node_modules/react-scripts/scripts/utils/createJestConfig.js:84`, ключ в списке `supportedKeys` и мержится с базовым конфигом |
| `TextEncoder` отсутствует | (1) `testEnvironment: 'node'` — не подходит, нужны DOM; (2) полифилл в `setupTests.js` | (2). Три строки из встроенного модуля `util`, без новых зависимостей |

Оба обходных пути помечены в коде как временные, со ссылкой на этот файл.

**Отдельно: `moduleNameMapper` указывает на `dist/development/...`** — внутренний путь пакета.
Это хрупко: смена внутренней структуры `react-router` при обновлении сломает маппинг. Приняли
осознанно, потому что альтернатива — откат обновления. Поломка будет громкой и понятной (тесты
не запустятся с явным сообщением), а не тихой.

### Шаг D — `devDependencies` (DH-005): почему перенесли не всё

Аудит предлагает перенести «build/test-пакеты». Разделили их:

| Пакет | Решение | Почему |
|---|---|---|
| `@testing-library/*` (4 шт.) | ✅ перенесены в `devDependencies` | Нужны только тестам. Netlify запускает лишь `npm run build` и тестов не касается |
| `react-scripts` | ❌ **оставлен в `dependencies`** | Netlify может выполнить установку без dev-зависимостей (например, при `NODE_ENV=production`), и тогда сборка упадёт с «react-scripts: not found» — прямо в прод, который автодеплоится с `main` |

Второе — сознательный отказ от буквального следования аудиту. `react-scripts` в `dependencies` —
это то, как `create-react-app` генерирует проект, и ровно по этой причине. Аудит оценивает DH-005
как **низкий** приоритет; ломать деплой ради низкоприоритетной перекладки — плохой размен. Проверить
поведение установки на Netlify мы не можем: доступа к панели нет.

### Шаг E — `engines`, `packageManager`, Node для Netlify (DH-003)

Значения выбраны не наугад. В истории репозитория есть коммит `dc5dea2`:
«ci: run on Node 24 so npm ci accepts the lockfile», и комментарий в `ci.yml` объясняет:

```yaml
# Node 24 ships npm 11, the version package-lock.json was generated
# with. On npm 10 `npm ci` rejects the lockfile as out of sync.
```

То есть проект **уже наступал** на расхождение версий, и оно уже ломало CI. Поэтому:

- `engines`: `node >=24`, `npm >=11` — фиксирует то самое ограничение, из-за которого чинили CI;
- `packageManager: npm@11.11.0` — версия, которой проверен этот lockfile;
- `netlify.toml` → `NODE_VERSION = "24"` — тот же мажор, что в CI.

До этой правки Netlify выбирал версию Node сам, то есть деплой мог читать lockfile иначе, чем CI, —
ровно тот риск, который аудит описывает как «публикационная сборка может интерпретировать lockfile
не так, как CI».

### Шаг F — install scripts (DH-004): почему не сделали

Аудит предлагает `ignore-scripts` или явный список разрешённых.

Не делаем, и вот почему. `ignore-scripts=true` в `.npmrc` отключает lifecycle-скрипты **всех**
пакетов при установке. Проверить последствия по-настоящему можно только там, где эта установка
выполняется, — в CI и в сборке Netlify. Локально мы можем проверить лишь одну из трёх сред.
Зависимости здесь — `three`, `@react-three/*`, `gsap`, то есть графический стек, где нативные или
постустановочные шаги вероятнее, чем в среднем проекте.

Риск: тихо сломанная сборка Netlify, которая деплоится на прод автоматически. Выигрыш: закрытие
находки **среднего** приоритета, у которой нет подтверждённого эксплуатируемого пути.

Правильный порядок — сначала включить обязательный CI-гейт (шаг 04, требует владельца), потом
менять режим установки, имея красный/зелёный сигнал до мерджа. Записали это в «что осталось».

### Шаг G — реестр исключений (DH-006)

Аудит: «Без владельца и срока нельзя отличить осознанный долг от незамеченного дрейфа». Создали
`frontend/DEPENDENCIES.md` — реестр с причиной, владельцем, датой пересмотра и планом устранения по
каждому принятому предупреждению.

Он понадобился немедленно и по неожиданной причине: после обновления роутера на рекомендованную
аудитом версию 7.18.2 появилось **новое** предупреждение —
[GHSA-qwww-vcr4-c8h2](https://github.com/advisories/GHSA-qwww-vcr4-c8h2), «RSC Mode CSRF Bypass»,
диапазон `>=7.12.0 <8.3.0`.

Разбор: предупреждение касается режима React Server Components и выполнения server actions. Проект —
клиентский SPA на `BrowserRouter`; RSC, data routers, `loader`/`action` и серверный рендеринг не
используются нигде. Уязвимый код в бандл не попадает.

Исправленной версии не существует: ветки 8.x ещё нет (`npm view react-router-dom dist-tags` →
`latest: 7.18.2`), а npm предлагает откат на 7.11.0. Уходить на более старый выпуск ради
неприменимого предупреждения — бессмысленно. Записано как EXC-002 с условием пересмотра «когда
выйдет 8.3.0».

## Что не сделано и почему: DH-002, замена `react-scripts`

Это главная находка аудита (высокий приоритет) и единственная невыполненная. Разбираем подробно,
потому что решение спорное и его должен принимать владелец.

### Что говорит аудит

> | Высокий | Заменить `react-scripts 5.0.1`: его вложенные пакеты содержат подтверждённые проблемы. |
> Цепочка запускается в CI и при сборке публикации; прямого исправленного выпуска `react-scripts` нет.

Это верно. `create-react-app` не сопровождается, исправлений не будет, и 16 из 18 оставшихся
предупреждений — оттуда.

### Почему мы не сделали это в этой сессии

**1. Проверить результат нечем.** Покрытие React-части — 2,23% (измерение из аудита тестов;
за сессию оно почти не изменилось, все новые тесты — про серверную часть и роутинг). E2E нет.
Основная ценность `/web` — WebGL-сцена `BlackHole.jsx` с инлайн-GLSL-шейдерами, скролл-таймлайны
GSAP и Lenis. Всё это `npm run build` собирает молча; сломанным оно окажется только в браузере.
Зелёная сборка после миграции **не будет** доказательством работоспособности сайта.

**2. Прод автодеплоится.** `main` → Netlify → katodevv.com без ручного шага. Ошибка миграции
уезжает к посетителям.

**3. Обязательного CI-гейта пока нет.** Он требует действий владельца (шаг 04). Делать самую
рискованную правку до включения защиты — неверный порядок.

**4. Это не «обновление зависимости», а смена тулчейна.** `react-scripts` даёт и сборку, и тестовый
раннер (`test:ci` — это `react-scripts test`). Миграция тянет за собой:

- `vite.config.js`; `index.html` переезжает из `public/` в корень; исчезает `%PUBLIC_URL%`;
  префикс переменных `REACT_APP_*` → `VITE_*`;
- замену раннера на Vitest — то есть переписывание `setupTests.js` и адаптацию всех шести
  тестовых файлов, включая обходные пути, добавленные на этом шаге;
- проверку сборки Three.js / `@react-three/*` / GSAP / Lenis и GLSL-шейдеров;
- правки `netlify.toml` и `.github/workflows/ci.yml`.

Приятный побочный эффект: обе поломки шага B (`exports` и `TextEncoder`) в Vite/Vitest исчезают
сами — они существуют только из-за Jest 27.

### План миграции для следующей сессии

Порядок именно такой; каждый пункт — отдельный коммит.

1. **Сначала включить обязательный CI-гейт** (шаг 04). Без него миграция не защищена ничем.
2. **Добавить page-level smoke-тесты** для `/`, `/bots`, `/apps` — с заглушками для
   `ResizeObserver`, `matchMedia`, canvas 2D и `scrollIntoView` (конкретный список выше). Это
   единственный способ получить автоматический сигнал о поломке страниц.
3. **Перевести тесты на Vitest**, оставаясь на `react-scripts` для сборки. Так тестовый и
   сборочный переезды разделяются, и каждый проверяется отдельно. На этом шаге уходят
   `moduleNameMapper` и полифилл `TextEncoder`.
4. **Перевести сборку на Vite.** Проверять: `npm run build` собирается; размеры бандлов
   сопоставимы с текущими (`main` ~90 kB gzip, самый крупный чанк ~262 kB — цифры из вывода сборки
   в `00-plan.md`); code splitting по маршрутам сохранился.
5. **Развернуть на deploy preview Netlify, не на прод.** Проверить руками: `/web` — чёрная дыра
   рендерится, скролл-джорни отрабатывает, лоадер уходит; `/bots` — маскот и анимации; `/apps` —
   drag-n-drop; на всех — виджет чата и отправка формы.
6. Только после этого — мердж в `main`.

**Критерий приёмки:** посетитель не видит разницы. Проверяется человеком в браузере, а не CI.

### Требует владельца

Нужно решение: делать миграцию отдельной сессией по плану выше — или считать EXC-001 приемлемым
долгом до появления другого повода (например, до того, как `react-scripts` перестанет
устанавливаться на новых версиях Node).

Мой ответ на вопрос «горит ли»: **нет**. Аудит безопасности, специально искавший эксплуатируемые
риски, поставил 92/100 и `react-scripts` не упомянул. Все 16 записей — инструменты сборки и
dev-сервера, не исполняющиеся ни у посетителя, ни на Netlify в рантайме.

Но долг реальный: сборщик из 2022 года уже, на этом самом шаге, помешал обновить обычную
зависимость и заставил добавить два обходных пути. Со временем такие столкновения будут чаще.

## Риски и что осталось

### Риски внесённых изменений

| Риск | Оценка | Смягчение |
|---|---|---|
| `react-router` v7 ведёт себя иначе в браузере | Низкий | 7 тестов на роутинг; API-поверхность из пяти вызовов; сборка зелёная. **Не проверено вживую в браузере** |
| `moduleNameMapper` сломается при обновлении роутера | Средний | Поломка громкая (тесты не запустятся с явным сообщением), не тихая. Уходит при переходе на Vitest |
| `overrides` дают несовместимую версию в глубине дерева | Низкий | Все три — патчи или крошечный пакет; проверено `npm ci` с нуля, тесты и сборка зелёные |
| Netlify установит без `devDependencies` | Низкий | `react-scripts` намеренно оставлен в `dependencies`; в `devDependencies` только тестовые пакеты, которые Netlify не использует |
| `NODE_VERSION = "24"` расходится с текущим образом Netlify | Низкий | Netlify поддерживает Node 24. Проверяется первым же деплоем |

### Что осталось

| Задача | Приоритет | Кому |
|---|---|---|
| Решение по миграции с `react-scripts` (DH-002) | Высокий | **владелец** |
| Ограничение install scripts (DH-004) | Средний | следующая сессия — **после** включения CI-гейта |
| Перенос `react-scripts` в `devDependencies` (остаток DH-005) | Низкий | вместе с миграцией; сейчас небезопасно |
| Пересмотр EXC-002 при выходе `react-router-dom` 8.3.0 | Низкий | следующая сессия |
| Page-level smoke-тесты | Средний | следующая сессия — предусловие для миграции |

### Проверка после деплоя

`NODE_VERSION` вступит в силу на следующем деплое. Стоит открыть лог сборки в Netlify и убедиться,
что в шапке указан Node 24, а не другая версия. Если сборка упадёт — откат через
**Deploys → Publish deploy** на предыдущий успешный (инструкция в `04-ci-gate.md`).
